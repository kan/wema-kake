## 2. 今回決めたこと

| 項目 | 決定 |
| --- | --- |
| ページ名と URL | URL はスラッグ、表示名は別に持つタイトル。URL は `/p/<slug>` |
| Wiki リンク | 付箋内の `<a href>` を正とする。独自記法は入れない |
| ルーティング | Hono |
| revert の衝突 | 部分適用。衝突したデルタだけスキップし、スキップした対象を返す |

### スラッグとタイトル

- スラッグは `^[a-z0-9][a-z0-9-]{0,63}$`。作成時に決め、後から変えない
- DO は `idFromName(slug)` で引く。D1 の `pages.name` にもスラッグを入れる
- タイトルは DO の `meta`（キー `title`）に持ち、D1 の `pages.title` に反映する。未設定のときはスラッグを表示する
- タイトルの変更は付箋のデルタではないので、`applyOps` とは別の DO メソッド `setTitle` で行う。接続中のクライアントへは `{ type: 'meta'; title: string }` を配信する（`ServerMsg` への追加）
- 存在しないスラッグを開いたら空のボードを表示する。D1 に行ができるのは最初の書き込みの後
- 新規作成の画面ではタイトルとスラッグを入力する。スラッグの初期値は短い乱数にしておき、手で書き換えられるようにする

### Wiki リンクの抽出

- 対象は、`href` のパスが `/p/<slug>` に一致する `<a>`。相対 URL と、自サイトのオリジンを持つ絶対 URL の両方を拾う
- 抽出は D1 反映（alarm）のときに全付箋の text に対して行い、そのページ発の `links` を入れ替える
- リンクを作る操作は wema の既存のリンク機能を使う。ページ名の補完などの入力補助は後から足す

### 3.2 `applyOps` の処理順

DO の書き込みは `applyOps(actor, clientId, opId, deltas, summary?)` だけにする。

1. 形の検証。デルタの型、数値が有限か、id の形式、1 回の `ops` のデルタ数と text の長さの上限
2. サニタイズ。`note:create` と `note:update` の text を HTMLRewriter に通す。**ここだけが非同期**
3. 以降は `await` を挟まずに実行する
   1. 重複の確認。同じ `client_id` と `op_id` の `ops` がすでにあれば、適用せずにその `seq` を返す（再接続後の再送への対処）
   2. `transactionSync` の中でデルタを順に検証しながら適用し、`seq` を進め、`ops` に記録する。検証に失敗したら例外で全体を巻き戻し、`reject` を返す
   3. 接続中の全クライアントへ `ops` を配信する
   4. alarm が未設定なら数秒後に設定する

手順 2 を先に済ませるのは、`transactionSync` のコールバックが同期でなければならないことと、`await` の間に別のメッセージが割り込めることによる。
状態の検証を `await` の後に置けば、検証から保存までの間に他の書き込みが入らない。

検証の規則（フェーズ 2 の実装で決めた）。

- 作成は、id が使用済みのとき、または接続線の両端がないときに拒否する
- 更新と削除は、対象がすでになければそのデルタを捨てる。他の人が先に消した付箋への操作で、送信元の変更全体を巻き戻さないため
- text の更新は、`before.text` が現在値と違えば拒否する。`before.text` は、送られてきた値とサニタイズした値のどちらかが現在値と一致すればよい。前者だけだと、送信元がサニタイズ前の text を持ったまま続けて編集したときに拒否される。後者だけだと、サニタイズの規則を変える前に保存した text を編集できなくなる
- text は 1 つ 500KB まで、1 回の `ops` は記録する内容の合計で 1.8MB まで（DO の SQLite の 1 行 2MB に収めるため）
- `applyOps` の呼び出しは DO の中で 1 つずつ順に処理する。サニタイズを待つ間に後続の呼び出しが先に進むと、同じクライアントの操作が送信順に適用されなくなるため
- 同じ `opId` の再送には、記録済みの結果（`fixups` を含む）を返す
- `note:update` の `zIndex` と `edge:update` の `from` / `to` は捨てる。値が変わらないキーも捨てる
- すべてのデルタを捨てた場合は `ops` に記録せず、`seq` も進めない

記録と配信の規則。

- `ops.body` と配信するデルタは、サーバーが実際に適用したものにする。更新の `before` と削除対象の内容は、送られてきた値ではなくサーバーの保存値で置き換える（取り消しを正しく行うため）
- 付箋を消すときに接続線が残っていたら、サーバーが `edge:delete` のデルタを作って同じ `ops` に入れる。wema は接続線の削除を先に送ってくるので、残るのは他の人が同時に足した接続線と、接続線を指定しない MCP からの削除である
- 送信元は自分の `opId` の `ops` を適用しない。そのため、サーバーが変えた分（サニタイズで変わった text、サーバーが足した接続線の削除）は `fixups` として返し、送信元だけが `applyRemote()` で適用する
- 更新の `after` にキーがなく `before` にあるものは「未設定に戻す」を表す。wema は接続線の折り畳みを解くときに `collapsed: undefined` を使うが、値が `undefined` のキーは JSON にすると消えるためである。受信側（`web/sync.ts`）もこの規則で復元する

### 3.3 WebSocket

- Hibernation API を使う。接続ごとの `clientId` と `actor` は `serializeAttachment` に入れる
- `actor` はクライアントの自己申告を使わず、Worker が Access JWT の email から `user:<email>` を作って DO に渡す
- `preview` と `presence` は保存せず、送信元以外へ中継する
- `hello` の `lastSeq` 以降の `ops` が残っていれば差分を、間引かれていれば `snapshot` を返す

### 3.4 D1 への反映

alarm ハンドラで次を行う。

1. 全付箋の text からタグを除いて連結し、`pages` を upsert する
2. リンクを抽出し、そのページ発の `links` を入れ替える
3. FTS のテーブルを更新する
4. 保持期間を過ぎた `ops` を消す

D1 は索引だが、**ページの一覧を持つのは D1 だけ**である（DO は名前から列挙できない）。
D1 を失うと、どのスラッグが存在するかが分からなくなる。D1 の Time Travel による復元を前提にし、FTS の仮想テーブルは、export の前に削除して後から作り直せるように、マイグレーションを分けておく。

### 3.5 取り消し

- `revert(seq, actor)` は `ops.body` から逆デルタを作り、デルタごとに現在値が元の `after` と一致するか確認する。一致しないものはスキップする
- 残ったデルタを `applyOps` と同じ経路で 1 つの `ops` として適用する。`summary` に元の `seq` を入れる
- 戻り値は、適用した数と、スキップした付箋と接続線の id、その理由
- 全部スキップになった場合は `ops` を作らず、`reverted_by` も書かない
- 付箋の削除を取り消すときは、同じ `ops` に入っている接続線の削除も一緒に戻る（逆順に適用するので付箋が先に復活する）

### 3.6 MCP

- `OAuthProvider` の `apiHandler` に `createMcpHandler` で作ったハンドラ、`defaultHandler` に Hono アプリを渡す
- ツールの実装は `BoardAccess`（ボードを読む、デルタを適用する、取り消す）越しに書く。サーバー版はページ DO の RPC を呼ぶ
- `actor` は `agent:<OAuth クライアント名>`。`created_by` と `ops.actor` に入る
- `add_notes` の id は Worker 側で `crypto.randomUUID()` を使って採番する
- `auto_layout` は wema が export する純粋なレイアウト関数を Worker で呼び、結果を `note:update` のデルタにして `applyOps` に渡す
- `revert_operation` が取り消せるのは、同じ `actor` が行った `ops` に限る

`createMcpHandler`、`OAuthProvider`、Access for SaaS の 3 つを組み合わせた公式サンプルは見つからなかった。
フェーズ 6 で実際に組み合わせ、`McpAgent` を使わずに動くことをテストで確かめた。

- `OAuthProvider`（1.2.1）は `resourceMetadata.resource`（MCP サーバーの正式な URL）を必須にしている。サイトの URL は実行時にしか分からないので、Worker の入口でオリジンごとに `OAuthProvider` を作って使い回す。`SITE_ORIGIN` があればそれを使い、空ならリクエストのオリジンを使う
- `createMcpHandler` は、localhost に届いたリクエストでだけ `Host` ヘッダーを検査する（DNS リバインディング対策）。本番のホスト名では検査しない
- MCP のサーバーは、同時に走るリクエストで共有できない。リクエストごとに `McpServer` を作る
- `@modelcontextprotocol/server` と、テスト用の `@modelcontextprotocol/client` は 2.0.0 を直接の依存にした。`agents` が同じ版を使う

### 3.7 画面

画面は wema のボードを中心に作り、ページの一覧も付箋の集合として表す（2026-10-03 に決めた）。

#### 一覧のボード（`/`）

- ページ 1 つを付箋 1 枚で表す。付箋には表示名（ページへのリンク）、本文の冒頭、更新日を出す
- ページ間のリンク（D1 の `links`）を接続線で表す。A から B へのリンクがあれば、A の付箋から B の付箋へ矢印を引く
- リンク先がまだ作られていないページは、色を変えた「未作成」の付箋として出し、線も引く。開いて書き込めばページができる
- 配置は開くたびに自動で決め、保存しない。計算は `src/web/index-board.ts` で行う
  - リンクでつながったページは、まとまりごとの階層で並べる（リンク元が上、リンク先が下）。1 つの階層のページが多いときは、複数の行へ折り返す。wema の `computeAutoLayout` は 1 つの階層を横 1 列に並べるので、リンクの多いページがあると横に長くなりすぎる。そのため使うのをやめた
  - まとまりは左上から順に詰め、つながりのないページはその下に、更新の新しい順に格子で並べる
  - 全体の幅は、ページが少なければ表示領域に収まる幅とする。多ければ、全体が表示領域と同じ縦横比になる幅まで広げる。全体を表示しても、縦に細長くならない
- リンクの線は、細く薄い色にして、付箋の後ろを通す。付箋にポインタを載せている間は、そのページにつながる線だけを目立たせる
- 付箋にポインタを載せると、付箋の右上に、表示名の変更とページの削除のボタンが出る。未作成のページの付箋には出ない。スラッグは変えられない
- ヘッダーに、全体が収まるように縮小するボタンと、付箋全体の中央へ移動するボタンがある。一覧では、全体が収まるように、縮小の下限を 5% にしてある（wema の既定値は 25%）
- ボードは wema の参照モード（viewOnly）で出す。編集の UI は出ず、付箋はドラッグできるが、再読み込みで戻る
- 検索欄に入力すると、一致するページの付箋だけを残す。残った付箋の位置は変えない。残った付箋同士の線はそのまま出す
  - 一致の判定は、サーバーの検索（表示名と本文。3 文字以上は全文検索、3 文字未満は部分一致）と、手元での表示名とスラッグの部分一致の和にする。未作成の付箋は検索の索引にないので、スラッグの部分一致だけで判定する
  - 検索語は URL（`/?q=`）へ入れる。再読み込みしても、URL を共有しても、同じ絞り込みになる
- 新規ページは、表示名とスラッグを入力して作る（`POST /api/pages/<slug>`）。スラッグの初期値は短い乱数にする。すでにあるスラッグは断り、既存のページの表示名を書き換えない

一覧のためのデータは `GET /api/index` で、ページとリンクをまとめて返す。

#### ページの画面（`/p/<slug>`）

- 見出しに、一覧へ戻るリンク、表示名（クリックで編集）、同期の状態を出す
- バックリンク（このページへリンクしているページ）を出す
- agent の操作の一覧と、取り消しボタンを出す
- ページの削除を出す

#### 調べて分かった制約と対処

| 制約 | 対処 |
| --- | --- |
| wema にスクロールとズームがなく、ボードは表示領域の大きさに固定される。はみ出した付箋には届かない。通常のページにも同じ制約がある | wema v0.6.0 のパンを使う（ホイール、中ボタンのドラッグ、Space + 左ドラッグ。参照モードでは左ドラッグでも動く）と、v0.7.0 のズーム（Ctrl / Cmd + ホイール、ピンチ）を使う |
| wema に付箋を隠す API がない | wema v0.5.0 の `setNoteFilter()` を使う |
| 付箋内のリンクは、wema が常に新しいタブで開く | wema v0.5.0 の `onLinkClick` を使う。サイト内のリンクは同じタブで開く。一覧とページの両方に入れてある |
| 一覧への反映は、変更の 5 秒後になる（D1 への反映が遅れるため） | そのままにする。新規ページは作った直後にそのページへ移動するので、一覧に出ない時間は目立たない |
| 一覧は 500 ページまで | 新しい順の 500 件を出す。検索の上限も 500 件にそろえる |

上の 3 つは、wema-kake 側の回避策ではなく、wema 側で対応することにした。2026-10-03 に wema の開発セッションへ依頼し、絞り込みとリンクは同日の v0.5.0 に入った。

一覧のボードは、v0.5.0 を使って 2026-10-03 に実装し、ブラウザで次を確かめた。

- 付箋と接続線が出る。未作成のページも付箋として出る
- 本文の語とスラッグで絞り込める。絞り込んでも付箋の位置は変わらない
- 検索語つきの URL を開くと、絞り込んだ状態になる
- 付箋のリンクは同じタブで開く

パンは 2026-10-03 の v0.6.0 に入った。それまで一覧に入れていた仮の対処（ボードを付箋の範囲と同じ大きさにして、外側の要素をスクロールさせる）は外した。ボードを置く要素は表示領域の大きさに固定し、通常のページも、はみ出した付箋へパンで届く。

ズームは 2026-10-04 の v0.7.0 に入った。一覧では、絞り込みの後に `fitToContent()` を呼び、残った付箋がすべて見える位置と倍率にする（等倍より大きくはしない）。検索語を消すと、開いたときの位置と等倍へ戻す。v0.7.0 では、操作でパンできる範囲が付箋の周囲（余白 200px）までに限られる。ボードの上の Ctrl / Cmd + ホイールは、ブラウザのページのズームではなくボードのズームになる。ズームのボタンはまだなく、フェーズ 6.5 で足す。

wema のパンとズームの設計（kan/wema#52）には、次の 2 点を回答し、v0.6.0 はそのとおりに実装された。

- 参照モードでは、空いている場所の左ドラッグをパンに割り当ててよい。ラバーバンド選択は Shift + ドラッグへ移す
- `exportData()` に表示位置（viewport）は含めない。表示位置は各クライアントの表示状態として扱う

リンクのフックで気を付ける点が 1 つある。`onLinkClick` に渡るのは、属性の値ではなく、ブラウザが解決した絶対 URL である。サイト内かどうかはオリジンの比較で判定する。属性の値の先頭が `/` かどうかで判定すると、`//other.example/` のような値でサイト外へ飛ばせてしまう。

#### ページの削除

- `DELETE /api/pages/<slug>`。ページの DO の内容（付箋、接続線、履歴、表示名）と、D1 の索引（`pages`、`links` のうちこのページ発のもの、`pages_fts`）を消す。取り消しはできない
- 接続中のブラウザは、専用のコードで接続を閉じる。ブラウザは再接続せず、一覧へ戻る（再接続すると、手元の未確定の操作でページが作り直されてしまう）
- 切断中だったブラウザは、閉じる通知を受け取れない。そこで、ページを作るたびに変わる値（epoch）をブラウザに渡しておき、再接続のときに送り返させる。サーバーの今の値と違えば、同じコードで接続を閉じる
- 削除の順番を待っている間に届いた書き込みは、削除の後に実行せず、拒否する
- 他のページからこのページへのリンクは残る。一覧では、未作成の付箋として出る
- 貼った画像は R2 に残る。どのページの画像かを記録していないためで、未対応のまま残る
- MCP には削除のツールを出さない（`AGENTS.md` の方針どおり）

## 4. 認証とパスの切り分け

| パス | 保護 | 処理 |
| --- | --- | --- |
| `/`、`/p/*`、静的ファイル | Access | Static Assets |
| `/api/*`、`/ws/*`、`/img/*` | Access | Worker。`Cf-Access-Jwt-Assertion` を `jose` で検証する |
| `/mcp` | Bypass | Worker。OAuth のアクセストークンを検証する |
| `/authorize`、`/token`、`/register`、`/callback`、`/.well-known/oauth-*` | Bypass | Worker（`OAuthProvider`） |

- Access アプリは、ホスト名全体を保護するものを 1 つと、Bypass するパスごとのものを作る
- Worker で JWT を検証する目的は 2 つある。Access の設定を誤っても未認証のリクエストを通さないことと、`actor` に使う email を得ること
- ローカル開発では Access がないので、開発用の変数で固定の email を使う。この変数は本番の設定には入れない

### フェーズ 5: 取り消し

- `revert`、`ops` の一覧取得

サーバー側は 2026-10-03 に実装した。残りは画面（agent の操作の一覧と取り消しボタン）である。3.5 節から変えた点は次のとおり。

- 付箋の作成の取り消しは、text が変わっていなければ消す。位置や色まで比べると、agent が貼った付箋を動かしただけで取り消せなくなる
- 取り消しの `ops` に `reverts`（取り消した対象の `seq`）を持たせた。要求元のブラウザは取り消しを手元に適用していないので、自分の `clientId` の `ops` でも `reverts` があればリモートの変更として適用する
- 取り消さない接続線がつながっている付箋は消さない。消すと、その接続線も一緒に消えるため
- 取り消しを取り消したら、元の操作の `reverted_by` を消す。元の操作をもう一度取り消せる
- 一部だけ取り消した場合も `reverted_by` を書くので、残りを後から取り消すことはできない

### フェーズ 6.5: ヘッダーの UI の整理

フェーズ 7 の前に、画面上部の UI を整理する。2026-10-04 に実装した（`src/web/toolbar.ts`、`src/web/icons.ts`）。案から変えた点は、この節の末尾に書いてある。

#### 目的

今のヘッダーには Wiki の機能（一覧へ戻る、表示名、同期の状態、リンク元、操作の履歴、削除）だけがある。付箋を操作するボタンはなく、付箋の追加はダブルクリック、Undo はキーボードでしか行えない。
wema のスタンドアロン版（`standalone/template.html`）には、付箋を操作するツールバーがある。これと Wiki の機能を 1 行のヘッダーにまとめ、常に見えるボタンを少なくする。

#### 今ある UI の棚卸し

wema のスタンドアロン版のツールバーにあるものと、wema-kake での扱い。

| スタンドアロン版の UI | wema の API | wema-kake での扱い |
| --- | --- | --- |
| Undo / Redo | `undo()`、`redo()`、`history:change` | 出す。取り消せるのは自分のブラウザでの操作だけ（agent の操作は「操作の履歴」から取り消す） |
| 付箋の追加 | `addNote()` | 出す |
| 整列、均等配置、自動レイアウト（ドロップダウン） | `alignNotes()`、`distributeNotes()`、`autoLayout()` | 出す。ドロップダウンのまま |
| 拡大、縮小、等倍、全体を表示 | `zoomTo()`、`fitToContent()`、`viewport:change` | 出す（wema v0.7.0 で入った。今は Ctrl / Cmd + ホイールでだけ操作できる） |
| ロック（readOnly） | `setReadOnly()` | 出さない。同期が最初の読み込みの間に同じ状態を使っていて、ボタンと食い違う |
| 参照モード（viewOnly） | `setViewOnly()` | メニューに入れる。読むだけのときに、編集の UI を隠せる |
| テーマ | `setTheme()` | メニューに入れる。ブラウザごとの設定として保存する |
| JSON の書き出し | `exportData()` | メニューに入れる |
| JSON の読み込み | `importData()` | 出さない。ボード全体を置き換える操作で、`history:commit` が発火しないので同期されない。入れるなら、差分をデルタにして送る設計が別に要る |
| 使い方（説明の付箋を置く） | `addNote()` | 出さない。説明の付箋がページの内容として保存され、他の人にも見えてしまう。使い方はメニューから別の画面で出す |
| ロゴ、GitHub へのリンク、付箋の数 | なし | 出さない |

wema-kake にしかないもの。

| UI | 今の場所 | 整理後 |
| --- | --- | --- |
| 一覧へのリンク | ヘッダーの左端 | そのまま |
| 表示名（クリックで編集） | ヘッダーの左 | そのまま。スラッグは `title` 属性で出す |
| 同期の状態（接続中、保存中、オフライン） | 表示名の右に文字で出す | 表示名の横の小さな印にする。同期済みのときは何も出さない。文言は `title` 属性と、オフラインのときだけ文字で出す |
| 一時的な通知（競合で取り消した、など） | ヘッダーの中に文字で出す | ボードの上に重ねて出す。ヘッダーの幅を取らず、他の要素が動かない |
| リンク元 | ヘッダーの右に、ページ名を並べる | 件数だけのボタンにし、押すと一覧が開く。リンク元が多いとヘッダーがあふれるため |
| 操作の履歴 | ヘッダーの右のボタン。押すと右にパネルが開く | アイコンのボタンにする。パネルはそのまま |
| ページの削除 | ヘッダーの右端のボタン | メニューの末尾へ移す。常に見える場所に置かない |

#### 配置の案

ヘッダーは 1 行で、3 つの区画に分ける。

```
[一覧] 表示名 ●   |   ↶ ↷ | ＋ | 整列▾ | − 100% ＋ ⤢   |   リンク元 3  履歴  ⋯
 左: 場所                中央: 付箋の操作                    右: Wiki の機能
```

- 左: 今いる場所を示す。一覧へのリンク、表示名、同期の状態の印
- 中央: 付箋を操作するボタン。アイコンだけにし、説明は `title` 属性で出す。区切りは細い線にする
  - Undo / Redo、付箋の追加、整列のドロップダウン、ズーム（縮小、倍率、拡大、全体を表示）
  - 選択がなくて使えないボタン（整列など）は、隠さずに無効の表示にする。位置が動かないようにするため
- 右: Wiki の機能。リンク元の件数、操作の履歴、メニュー（⋯）
  - メニューの中身: 参照モード、テーマ、JSON の書き出し、使い方、ページの削除（区切り線の下に置く）

煩くしないために決めておくこと。

- 常に見えるボタンは、中央の 9 個と右の 3 個までにする。それ以外はメニューへ入れる
- 文字のボタンは使わず、アイコンにそろえる。アイコンは wema のスタンドアロン版と同じ絵柄を使う（同じ操作が同じ絵になる）
- 色は、無彩色を基本にする。色を使うのは、オフラインの印と、削除の項目だけにする
- 幅が狭いときは、中央の区画のうちズームと整列をメニューへ移す。左と右の区画は残す

一覧の画面（`/`）も同じ骨組みにする。

- 左: サイト名
- 中央: 絞り込みの入力欄と件数、ズーム
- 右: 新規ページ。入力欄を常に出さず、ボタンを押したときに表示名とスラッグの入力欄を開く

#### 実装の方針

- ヘッダーを組み立てる処理を `src/web/toolbar.ts` に切り出し、ページの画面と一覧の画面で共有する。今は `page-view.ts` と `index-view.ts` がそれぞれ組み立てている
- ボタンの有効と無効は、wema のイベントから決める（`history:change`、選択の変更、`viewport:change`）。自前の状態は持たない
- 参照モードとテーマは、ブラウザごとの設定として `localStorage` に保存する。ページの内容と同期の対象には含めない
- 最初の同期が済むまでは、中央の区画のボタンを無効にする（その間はボードが readOnly のため）

#### 実装で案から変えた点

- 参照モードには wema v0.7.1 が要る。v0.7.0 までは、参照モードの間に `importData()`（再接続でのスナップショットの読み直し）があると、終えるときに読み直す前の位置へ付箋が戻り、サーバーの内容と食い違った。実装の途中で見つけて wema 側へ報告し、v0.7.1 で直った
- 幅が狭いとき（760px 以下）は、整列とズームのボタンをメニューへ移さず、隠すだけにした。ズームは Ctrl / Cmd + ホイールでできる
- 一覧の「＋ 新規ページ」だけは、文字のボタンにした。一覧の画面で最も使う操作なので、アイコンだけにすると見つけにくい。リンク元の件数も文字で出す
- リンク元が 0 件のときは、ボタンを出さない
- 使い方は、重ねて出す画面（`dialog`）にした
- Ctrl / Cmd + A の全選択を足した（wema のスタンドアロン版にあり、ライブラリにはない。整列のボタンと合わせて使う）
- ページの画面に常に見えるボタンは、中央の 8 個と右の 2 個になった。リンク元があるときは、その件数のボタンが加わる

ブラウザ（Chromium）で次を確かめた。

- 付箋の追加、Undo と Redo、整列が、ボタンから行え、保存される
- ズームのボタンで倍率が変わり、倍率の表示が追従する
- メニューから、参照モード、見た目の切り替え、JSON の書き出し、使い方、削除ができる。参照モードと見た目は、読み込み直しても残る
- リンク元が 20 件あっても、幅 1024px でヘッダーが 1 行に収まる
- 一覧の新規ページは、ボタンを押すと入力欄が開く

#### 決めていないこと

- 表示位置と倍率を、ページごとにブラウザへ保存して復元するか（スタンドアロン版は保存している）。保存すると決めた。実装は、フェーズ 6.6 で行う
- JSON の読み込みを入れるか。入れる場合は、同期する方法の設計が先に要る
- スマートフォンの幅での配置。wema のタッチ操作（1 本指のパン）が未実装なので、それが入ってから決める

#### 完了の条件

- ページの画面で、マウスだけで付箋の追加、Undo、整列、ズームができる
- 幅 1024px のウィンドウで、ヘッダーが 1 行に収まる。リンク元が 20 件あっても収まる
- 一覧の画面とページの画面で、同じ場所に同じ種類の操作がある

### フェーズ 6.6: 入れ子ボードとページの階層

ページを、別のページの中へ子ページとして置けるようにする。子ページへは、ズームインするように入っていく。あわせて、一覧にはルートのページだけを出す。

2026-10-04 に、前半（実装の順序の 2 から 5 と 8）と後半（6 と 7）の両方を実装した。前半は、階層の記録、子ページの付箋、一覧、削除の扱い、MCP である。後半は、読み込みなしの画面の切り替えと、階層を移るときのズームの演出である。実装で設計から変えた点は、この節の末尾に書いてある。

目的は 2 つある。

- 付箋から子ページへ、ズームインするように入っていける体験を作る
- 全体の見通しを良くする。今はページがフラットで、すべてのページが一覧に出る。一覧に出すのをルートのページだけにして、子ページと孫ページへは、親ページの中からたどる

wema のロードマップにあった構想（付箋が子のボードのデータを持つ `children?: WemaBoardData`）を、wema-kake が引き継ぐ。wema にはこの構造を足さない（2026-10-04 に wema の開発セッションから提案があり、採用した）。

#### 決めたこと

- **子ボードはページで表す。** ボードのデータは入れ子にしない
  - 同期の単位（ページの DO と、wema の履歴デルタ）は入れ子に対応していない。入れ子にすると、1 つの DO に全階層が載り、`applyOps`、取り消し、同期のプロトコルのすべてに手が入る
  - ページで表せば、同期、取り消し、MCP は今のまま使える
- **リンクにすることと、子ページとして置くことを分ける。** それぞれの意味と、分ける理由は次のとおり
  - リンク: 付箋の本文にある Wiki リンク（`<a href="/p/<slug>">`）。今までどおりで、階層には関与しない。一覧では線になる
  - 子ページとして置く: ページを、別のページのボードの上に、専用の付箋（子ページの付箋）として置く操作。階層は、この操作だけで決まる
  - 分ける理由: 階層を付箋の本文の形から決めると、説明を 1 行足しただけで階層が変わる。付箋の編集のたびに、ページが一覧に出たり消えたりもする。明示の操作に分ければ、どちらも起きない
- **親は 1 つだけにする。** 階層は木になる。輪は作れない。パンくずとルートの判定は、データから一意に決まる。別のページからも参照したいときは、リンクを使う
- **子ページの付箋を削除すると、子ページはルートへ戻る。** ページは消えず、一覧に戻る。Undo で付箋を戻すと、子ページに戻る
- **一覧に出すのは、ルートのページ（親のないページ）だけにする。**

#### 用語

- 子ページの付箋: 子ページを表す専用の付箋。本文は持たず、子ページの表示名と付箋の枚数を出す。押すと子ページへ入る
- 子ページ: 子ページの付箋が指すページ。その先の子ページを、孫ページと呼ぶ
- 親ページ: 子ページの付箋が置いてあるページ
- ルートのページ: 親のないページ

#### 作るもの

1. 子ページの付箋
   - 付箋のデータに、子ページのスラッグを持たせる。本文とは別の項目にする
   - 付箋には、子ページの表示名と付箋の枚数を出す。他の付箋と見分けられる見た目にする
   - 子ページの付箋の配置を、SVG で簡易に再現して出す（付箋の位置、大きさ、色だけ。画面の縮小は出さない）
2. 置く操作と外す操作
   - 「子ページを作る」: 新しいページを作り、今のページに子ページの付箋を置く
   - 「既存のページを置く」: ルートのページを選び、今のページの子にする。すでに親のあるページは、外してから置く
   - 「外す」: 子ページの付箋を削除する。子ページはルートへ戻る
   - 自分自身と、自分の先祖は置けない（輪になるため）
3. 階層の記録
   - 子ページの DO に、親ページのスラッグを持たせる（`meta` の `parent`）。親が 1 つであることと、輪にならないことは、ここで検査する
   - D1 の `pages` に `parent` の列を足す。一覧、検索、MCP は、この列を見る
4. 一覧
   - `GET /api/index` は、ルートのページだけを返す。付箋に、子ページの数を出す
   - 線は、ルート同士のリンクだけにする。子孫のページから出ているリンクは、線にしない
   - 絞り込みは、子ページと孫ページも対象にする。子孫が一致したときは、そのルートの付箋を残し、子孫に一致がある旨と数を出す
5. ページの画面
   - ヘッダーの左の区画に、ルートからのパンくずを出す。URL を直接開いたときも出る
   - 表示位置と倍率を、ページごとにブラウザへ保存し、開いたときに復元する
6. ズームインの遷移
   - 子ページの付箋を押すと、その付箋へ寄ってから子ページへ切り替える。子ページは、全体が収まる倍率から始める
   - パンくずで親へ戻ると、親ページの元の表示位置へ戻る。遷移は、入るときの逆にする
   - 修飾キーつきのクリックと中ボタンは、新しいタブで開く
7. MCP
   - `read_board` は、子ページの付箋を、子ページのスラッグつきで返す
   - `list_pages` と `search_pages` は、今までどおり全ページを返し、親ページのスラッグを添える
   - 本文に、ページへのリンクの書式（`[[slug]]`）を足す。`add_notes` と `update_notes` で書け、`read_board` で読める（課題の 10）
   - ページの作成と、子ページとして置く操作は、ツールにしない（課題の 9）

#### 見つかった課題

設計の前に調べて分かったこと。それぞれの「対処の案」のとおりに進めると、2026-10-04 に決めた。

1. **wema の付箋には、利用側が自由に使える項目がない。** 子ページのスラッグを、本文とは別に持たせられない。項目は、`exportData()`、履歴デルタ、`applyRemote()` を通って保たれる必要がある
   - 対処の案: wema に、付箋へ利用側のデータを持たせる項目を足してもらう（issue を立てる）。サーバーの検証（`src/worker/validate.ts`）とスキーマにも、同じ項目を足す
   - 結果: kan/wema#53 として依頼し、wema v0.8.1 で `WemaNote.meta`（値は文字列だけの `Record<string, string>`）が入った。`updateNote()` は `meta` の全体を置き換える。デルタにも `meta` の全体が入る。付箋の複製では引き継がれない。大きさと形の上限は wema にはないので、サーバーで検証する
2. **付箋の描き方を、利用側で差し替える手段がない。** 付箋の中身は wema がサニタイズして描く。子ページの付箋は、本文の代わりに、子ページの表示名と付箋の枚数を出したい。本文の編集もさせたくない
   - 対処の案: wema に、付箋の中身を利用側が描く口を足してもらう（1 と同じ issue に入れる）。一覧の画面の操作ボタン（`src/web/index-actions.ts`）のように上へ重ねる方法は、常に出す表示には向かない。パン、ズーム、ドラッグ、リサイズのたびに位置を合わせる必要がある
   - 結果: 同じ kan/wema#53 で、wema v0.8.1 に `renderNote` オプションと `refreshNote(id)` が入った。`renderNote` が `true` を返した付箋は、本文の代わりに利用側の DOM を出し、本文を編集できない。呼ばれるのは、付箋を作ったとき、`text` か `meta` が変わったとき、`refreshNote(id)` を呼んだとき。利用側の DOM はサニタイズを通らないので、表示名などは `textContent` で入れる
3. **階層の記録が、2 か所になる。** 子ページの付箋は親ページの DO にあり、`parent` は子ページの DO にある。2 つの DO の書き込みは、まとめて行えない。片方だけが成功すると、食い違う
   - 対処の案: 正とするのは、子ページの DO の `parent` とする。親ページの DO は、子ページの付箋を作るデルタを適用する前に、子ページの DO へ問い合わせて `parent` を設定する。断られたら、デルタを拒否する。付箋を削除するデルタでは、適用した後に `parent` を消す。食い違い（付箋はあるのに `parent` が違う）は、付箋の側を「外れている」と表示して、利用者が消せるようにする
   - 影響: `applyOps` が、他の DO を呼ぶようになる。取り消し（revert）と Undo で付箋が戻るときも、同じ検査を通る。断られることがある
4. **輪の検査は、親をたどる必要がある。** 置こうとしているページが、今のページの先祖でないことを確かめる
   - 対処の案: 親ページの DO から、`parent` を順にたどる（DO の呼び出しが、階層の深さの回数になる）。深さの上限は 5 にする
5. **画面の切り替えが、ページ全体の読み込みになっている。** サイト内のリンクは `location.assign()` で開く（`src/web/dom.ts`）。読み込みの間に画面が白くなるので、ズームインしても、つながった動きに見えない
   - 対処の案: ページからページへの移動を、読み込みなしの切り替えにする（History API）。ボード、同期、`document` に付けたリスナー（パネルを閉じる処理、Ctrl + A）を片付ける処理が要る。今は、画面を作る関数に片付けの口がない
6. **表示位置の遷移に、動きを付ける手段がない。** wema の `setViewport()` と `zoomTo()` は、すぐに切り替わる
   - 対処の案: wema-kake の側で、`requestAnimationFrame` ごとに `setViewport()` を呼ぶ。足りなければ、wema に issue を立てる
7. **ページを削除したときの、親と子の扱いを決める必要がある。** 今の削除は、そのページの内容と索引を消すだけである
   - 対処の案: 子ページを削除したら、親ページにある子ページの付箋も消す（子ページの DO が親を知っているので、親ページの DO へ削除のデルタを送る）。親ページを削除したら、子ページはルートへ戻す（付箋の削除と同じ扱い。子孫ごと削除はしない）
8. **一覧の 500 ページの上限は、ルートの数へ掛かるようになる。** 今は全ページのうち新しい順の 500 件で、絞り込みの上限も 500 件にそろえてある
   - 対処の案: 一覧の上限はルートの 500 件にする。絞り込みは、一致したページから `parent` をたどって、ルートを求める
9. **MCP のツールは、ページを作れず、置くこともできない。** ページの作成はツールでは行わないと決めてある（人が画面から作る）
   - 対処の案: このフェーズでは、読むだけにする（作るものの 7）。LLM にページの作成と階層の操作を許すかは、LLM との連携を実際に使ってから決める
10. **MCP のツールは、リンクを読み書きできない。** `add_notes` と `update_notes` の本文はプレーンテキストで、リンクはエスケープする。`read_board` は、リンク先を捨てる。階層とは別の話だが、LLM は、ページ同士の関連を読み書きできない
    - 対処の案: ページへのリンクの書式を 1 つ足す（`[[slug]]`）。読み書きで同じ書式にする。外部の URL へのリンクは足さない。このフェーズに入れる

リンクと分けたことで、なくなった課題がある。記録として残す。

- 階層が付箋の本文の形で決まるので、説明を足すと階層が変わる
- 付箋の編集のたびに、ページが一覧に出たり消えたりする
- 2 つのページが互いを子にすると輪ができ、ルートがなくなる
- URL を直接開いたときに、親が決まらない

#### 実装の順序

1. wema への依頼（課題の 1 と 2）。付箋に利用側のデータを持たせる項目と、付箋の中身を利用側が描く口。2 から 5 と 7 は、これを待つ。wema v0.8.1 で入り、2026-10-04 に取り込んだ
2. 階層の記録（課題の 3 と 4）。DO の `parent`、D1 の列、置く操作と外す操作の API
3. 子ページの付箋の表示と、置く操作と外す操作の画面
4. 一覧をルートだけにする。絞り込み、子ページの数、パンくず（課題の 8）
5. ページの削除の扱い（課題の 7）と、MCP の読み取り
6. 読み込みなしのページの切り替え（課題の 5）
7. ズームインの遷移（課題の 6）

8. MCP の本文に、ページへのリンクの書式を足す（課題の 10）

5 までで、一覧にルートだけが出て、親ページから子ページへたどれる状態になる。6 と 7 は、その移動をズームインの動きにする部分で、後に回せる。8 は、サーバーだけで済み、他の項目と wema の対応のどちらにも依存しない。wema の対応を待つ間に、先に進められる。

#### 決めていないことと、後から決めたこと

- LLM に、ページの作成と、子ページとして置く操作を許すか（課題の 9）。LLM との連携を実際に使ってから決める。このフェーズでは決めない

次の 5 つは、2026-10-04 に決めた。どれも「現時点では」の決定で、使ってみて見直す。

- 一覧の絞り込みで子孫のページが一致したときは、その子孫を持つルートの付箋を残す。子孫に一致があることと、その数が分かる表示を、ルートの付箋に出す
- 子孫のページから出ているリンクは、一覧では線にしない。線にするのは、ルート同士のリンクだけ
- 階層の深さの上限は 5 にする。ルートを 1 段目と数えて、5 段目まで置ける
- 表示位置と倍率は、ページごとにブラウザへ保存する（フェーズ 6.5 からの持ち越し）
- サムネイル（画面の縮小）は出さない。代わりに、子ページの付箋の配置を SVG で簡易に再現して、子ページの付箋に出す

決めたことに伴って、実装で扱う点がある。

- 絞り込みの表示: 今の絞り込みは、付箋を隠すだけで、付箋の中身は書き換えない。一致の数を出すには、絞り込みのたびにルートの付箋の中身を書き換える。検索の API は、一致したページのルートを返す（課題の 8）
- 深さの上限: 置く操作のときに、親をたどって検査する（課題の 4 と同じ処理）。子孫を持つページを置くときは、置いた後の最も深い段も数える。子孫の深さは、D1 の `parent` から求める案だったが、実装では DO をたどって数えることにした（下の「実装で設計から変えた点」）
- 表示位置の保存: `localStorage` に、スラッグごとに保存する。保存があれば、その位置と倍率で開く。なければ、全体が収まる倍率で開く。ズームインの遷移の行き先と、パンくずで親へ戻るときの行き先も、同じ値を使う。件数に上限を設け、古いものから捨てる
- 配置の再現: 子ページの付箋の位置、大きさ、色だけを使う（本文と接続線は使わない）。親ページを開くたびに子ページの DO を 1 つずつ読むと、子ページの数だけ呼び出しが増える。そこで、索引を作るとき（alarm）に、配置を小さな JSON にして D1 の `pages` へ書いておき、子ページの情報と一緒に返す。枚数に上限を設ける。反映は、他の索引と同じく変更の 5 秒後になる

既存のページは、子ページとして置くまではすべてルートのままになる。移行の作業は要らない。

#### 実装で設計から変えた点（前半）

- 置く操作と外す操作の API は作らなかった。子ページの付箋は、ふつうの付箋と同じくデルタで作り、消す。検査は、デルタを適用する `applyOps` と取り消し（`revert`）の中で行う。Undo、貼り付け、MCP の `delete_notes` も、同じ検査を通る
- 深さは、D1 の索引ではなく、子ページの DO を順にたどって数える。D1 への反映は変更の数秒後なので、置いた直後に続けて置くと、6 段目以降を置けてしまうためである
- 輪の検査は 2 回行う。置く前と、子にした後である。他のページで同時に置く操作があると、置く前の検査だけでは、3 ページ以上の輪を見逃す
- 2 つの DO の食い違いは、索引の更新で両側から直す。親ページの側は、付箋のない子をルートへ戻す。子ページの側は、親がなくなっていればルートへ戻る
- 子ページの付箋の表示名と枚数は、索引にあれば索引から、まだなければ子ページの DO から取る。作って置いた直後でも出る。付箋の配置の再現は索引から取るので、索引ができるまで（数秒）は出ない。別のタブから戻ったときと、読み込み直したときに新しくなる
- 置けなかった理由は、決まった形の文字列（`child page: <理由>: <スラッグ>`）で返す。画面と agent が、同じ文字列を読む
- 一覧で、ルートのページを削除したとき、その子ページ（ルートへ戻る）は、一覧を読み込み直すまで出ない
- MCP の本文で、リンクの文字がスラッグと違うリンクは、`文字 [[slug]]` の形で読める。書くときは `[[slug]]` だけで、文字はスラッグになる

前半について、ブラウザ（Chromium）で次を確かめた。

- 子ページを作って置くと、子ページの付箋ができ、表示名、付箋の枚数、配置の再現が出る
- 子ページの付箋から子ページへ入り、パンくずで親へ戻ると、前に見ていた表示位置で開く
- 一覧には親だけが出て、子ページの数が出る。子ページの本文で絞り込むと、親の付箋が残り、一致の数が出る
- 別の親がある子ページは置けず、理由が通知される
- 子ページの付箋を削除するとルートへ戻り、Undo で子に戻る。子ページを削除すると、親ページの付箋も消える

#### 実装で設計から変えた点（後半）

- 読み込みなしの切り替えは、ページ同士だけでなく、一覧とページの間にも入れた。階層は、上から、一覧、ルートのページ、子ページの順として扱う。一覧の付箋からページへ入るときも、ページから一覧へ戻るときも、同じ演出が入る
- 演出は 2 段にした。入るときは、押した付箋へ寄ってから切り替え、切り替えた先は小さい状態から広がる。戻るときは、全体を縮めてから切り替え、切り替えた先は、戻ってきたページの付箋から広がる。それぞれ 0.22 秒。OS やブラウザの「動きを減らす」設定があれば、演出は入れない
- 表示位置の遷移は、wema-kake の側で、フレームごとに `setViewport()` を呼んで作った。wema への依頼は要らなかった
- 表示位置の保存は、演出が済んでから始める。演出の途中の位置と、切り替えの前に寄った位置は、見ていた場所として保存しない。全体が収まる倍率にしただけのページも、動かすまでは保存しない（付箋が増えれば、次に開いたときに、収まる倍率を取り直す）
- 切り替える前に、保存中の変更を送り終えるのを待つ（最長 1.5 秒）
- 画面全体に付けるリスナーは、画面ごとの signal で外す。画面が終わるときに、同期を止めて、ボードを破棄する（`src/web/navigation.ts`）
- 付箋の中のリンク（Wiki リンク）と、ブラウザの「戻る」「進む」も、読み込みなしで切り替わる。こちらには、演出を入れていない
- 一覧の表示位置は、ブラウザには保存しない。同じ絞り込みの一覧へ戻ってきたときだけ、離れたときの位置から始める（ページを読み込み直すと消える）
- ページの削除と、認証の切れた後の読み込み直しは、今までどおり、ページ全体の読み込みで移る

後半について、ブラウザ（Chromium）で次を確かめた。

- 階層を下る操作（一覧からページへ、ページから子ページへ）で、読み込み直しが起きない
- 階層を上る操作（パンくずで親へ、一覧へ）でも、読み込み直しが起きない
- 入った直後は小さい状態から広がり、戻った直後は付箋へ寄った状態から広がる。落ち着く位置は、前に見ていた場所になる
- 切り替えた先で、編集と保存ができる。離れる直前の変更も、失われない
- 「戻る」と「進む」で、内容が切り替わる。連打しても、履歴は 1 つしか増えない
- Ctrl + クリックは、新しいタブで開く

#### 完了の条件

- 子ページの付箋が、他の付箋と見分けられる
- 一覧に、ルートのページだけが出る。ページを子として置くと一覧から外れ、子ページの付箋を削除すると一覧に戻る
- 付箋の本文を編集しても、リンクを足しても、階層は変わらない
- 1 つのページを、2 つのページの子にはできない。自分の先祖を、子として置けない
- 一覧の絞り込みで、子ページと孫ページを探せる。子孫が一致したルートの付箋に、子孫に一致がある旨と数が出る
- 6 段目になる置き方は断られる
- ページを開き直すと、前に見ていた表示位置と倍率で開く
- 子ページの付箋に、子ページの付箋の配置が簡易に出る
- 子ページの付箋から子ページへ入り、パンくずで親ページの元の表示位置へ戻れる。その間、画面が白くならない
- LLM が、`read_board` で、どの付箋が子ページかを読める
- LLM が、MCP のツールで、ページへのリンクを読み書きできる
